# Toward a standard device attestation token for device assignment ([Video](https://www.youtube.com/watch?v=-zZrDuvgMgQ))

Presenter: Mathieu Poirier

The session "Toward a Standard Device Attestation Token for Device Assignment,"
presented by Mathieu Poirier at the Linux Plumbers Conference 2025, focused on
creating a unified, architecture-agnostic representation for device claims in
confidential computing.

## **Problem & Motivation**

- **Architectural Diversity:** Multiple architectures (like ARM, x86) are
  implementing device assignment into secure Virtual Machines (VMs), primarily
  for PCIe devices using standards like SPDM (Security Protocol and Data Model)
  and TDISP.
- **Need for Standardization:** Currently, different platforms may represent
  similar device claims in unique ways. A standard "token" format would simplify
  third-party verification and avoid redundant implementations across
  architectures.
- **Flexibility:** The goal is a generic representation that can be wrapped in
  platform-specific envelopes, allowing it to be used without forcing a
  one-size-fits-all approach on every hardware vendor.

## **Proposed Solution**

- **Entity Attestation Token (EAT):** The proposal uses the EAT profile to
  package device claims.
- **Technical Specification:** Defined using Concise Data Definition Language
  (CDDL), the specification includes:
  - **Envelopes:** A top-level token containing a nonce (for freshness) and
    submodules for various device types.
  - **Claim Sets:** Specific modules for SPDM-compliant devices (including
    certificates and measurement blocks) and legacy PCIe devices (representing
    config space).
- **Workflow:** Claims are collected from `sysfs` by a user-space agent in the
   VM, packaged into the standard token, and sent to a third-party verifier
   for authentication.

## **Key Discussion Points**

- **Vendor-Specific Claims:** Attendees raised concerns about how to handle
  unique hardware features not covered by SPDM. Mathieu explained that the SPDM
  standard already provides categories for custom measurements, and their token
  format is extensible to accommodate vendor-specific extensions.
- **Binding Evidence to VM Attestation:** A critical requirement is ensuring
  that a device's attestation is linked to the specific VM it is assigned to.
  Mathieu confirmed they have a scheme (especially for ARM) to group realm,
  platform, and device tokens into a single signed package.
- **Freshness and Performance:** There was a debate on how to ensure data isn't
  "stale." While SPDM uses nonces, some noted that re-negotiating SPDM for every
  VM request might be heavy. Suggestions included allowing the Trusted Security
  Manager (TSM) to cache and vouch for the freshness of device data.
- **Expanding Beyond PCIe:** Participants suggested making the format more
  generic to support other bus technologies like CXL and CHI. Mathieu agreed,
  stating that while the current focus is PCIe, the specification is
  designed to be bus-agnostic.
- **Authority of Measurements:** In the context of ARM's CCA, discussions
  clarified that while the RMM (Realm Management Monitor) oversees the VM, the
  device vendor is ultimately responsible for the measurements generated by the
  Device Security Manager (DSM).
